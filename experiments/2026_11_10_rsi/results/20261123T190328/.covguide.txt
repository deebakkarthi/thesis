About the Coverage App

The Jasper Coverage App provides coverage data in a formal proof environment to support the
formal proof in regard to the confidence of results and to bridge the gap with simulation coverage
(assisting in coverage closure). The Coverage App uses code coverage models (branch, statement,
expression, toggle, and FSM) and functional coverage models to represent both RTL structures and
user‑defined behaviors as Cover Items. Each Cover Item possesses reachability conditions,
allowing analysis of how constraints affect what the formal environment can exercise. In addition to
reachability (Stimuli) coverage, the Jasper Coverage app also reports Checker Coverage, showing
which RTL elements are actually being verified by the user’s properties to ensure thorough design
checking.

Introduction to Coverage

This chapter introduces the concepts, methodology, and tools related to coverage in hardware
verification, with a focus on the Jasper Coverage App. It provides foundational knowledge for
understanding how coverage supports verification completeness and quality. It comprises the
following sections:

     Coverage Overview

     Formal Coverage


Coverage Overview

Coverage is a metric used in hardware design and verification to measure how thoroughly a design
has been exercised by a set of test cases. It highlights which portions of the design have been
tested and which remain untested, guiding verification efforts toward comprehensive validation in
both formal and simulation-based verification context.



Coverage Goals
The primary goals of using coverage include:
      Identifying verification gaps: Pinpointing untested areas to guide targeted test development.
      Ensuring functional completeness: Verifying that all intended features and operations
      behave as expected.
      Reducing risk of undetected bugs: Catching corner cases and critical issues early in the
      design cycle.
      Structuring the verification process: Providing a methodical framework for planning and
      executing verification tasks.

Coverage in Formal versus Simulation-Based Verification
Coverage is a key concept in both formal and simulation-based verification, aiming to measure
verification completeness. While the goal is the same, the techniques and insights provided by

Formal Coverage
Formal coverage plays a critical role in the formal verification signoff process by offering rigorous
analysis of design reachability and completeness of the assertion set.



Formal Verification Workflow


Formal verification aims to test the design by using mathematical expressions to describe the
desired expected behaviors of the design. The formal verification process involves the following
steps:



March 2026                                           17                                    Product Version 2026.03
                                       Jasper Coverage App User Guide
                                  Introduction to Coverage--Formal Coverage



  1. Define verification goals and metrics.
  2. Write formal properties to describe expected design behavior.
  3. Run Jasper apps to analyze properties.
  4. Use the Coverage App to assess completeness and identify gaps on the verification.




Key Contributions of Formal Coverage


Here are the key contributions of Formal Coverage:
      Reachability Analysis: Detects unreachable or dead code due to environment setup or RTL
      bugs (Stimuli Coverage).
      Completeness Analysis: Measures how much of the design is covered by formal properties
      (Checker Coverage).
      Assert Bound Analysis: Evaluates how deep assertions verify the design (Coverage Bound
      Analysis).




Challenges
Formal Coverage can face challenges such as:
      State Space Explosion: For complex designs, the state space can become extremely large,
      making exhaustive formal verification computationally intensive and time-consuming.
      Scalability: Formal methods might struggle to scale effectively with very large designs,
      requiring innovative techniques and optimizations to manage complexity.
      Interpreting Results: Interpreting Formal Coverage results and translating them into
      actionable insights for design improvements and bug fixes can require specialized expertise.
Overcoming those challenges involves:
      Adopting a Coverage-Driven Methodology.
      Integrating formal and simulation results.
      Investing in team training and tool proficiency.

Jasper Coverage App Overview

The Jasper Coverage App provides a complete insight of verification completeness. Using Coverage App starts by understanding its main
concepts and how they interact with each other. The figure below lists the necessary steps for using the Coverage App.




  1. Comprehend Coverage Metrics
     Begin by understanding the three core metrics:
           Stimuli Coverage: Measures whether cover items are reachable under the current constraints.
           Checker Coverage: Measures how effectively assertions verify the design.
           Formal Coverage: The overall metric combining reachability and assertion completeness.
  2. Extract Cover items via Coverage Models
     Use code coverage models (branch, statement, expression, toggle, FSM) and functional coverage models (properties, covergroups) to
     generate cover items. These items represent the structural and behavioral elements of the design to be analyzed.
  3. Apply Coverage Types for Analysis
     Analyze the extracted cover items using the complementary types of coverage analysis:
           Stimuli Coverage Type: Determines if items can be exercised.
           Checker Coverage Type: Evaluates if items are verified by assertions, using COI, Proof Core Normal Precision, Proof Core High
           Precision, or Mutation.
           Coverage Bound Analysis: For assertions that do not converge, use bound analysis to assess how deeply the formal engine
           explored the design. This helps determine the quality and trustworthiness of bounded proofs.
  4. Interpret the Results
     Combine the results of stimuli, checker, and bound analysis to:
           Identify unverified or unreachable areas.
           Refine the verification environment.
           Improve assertion quality.
           Guide signoff decisions with confidence.
This chapter introduces the core concepts behind the Jasper Coverage App, focusing on how coverage is measured and how cover items are
extracted, deep diving on the supported coverage models and coverage types, and finally recommending a comprehensive methodology to
apply coverage on your verification efforts in the most effective way.


Coverage Metrics Overview
Coverage metrics provide a quantitative view of how thoroughly a design has been verified. In the Jasper Coverage App, three primary types of
metrics are used:
Stimuli Coverage
Stimuli coverage evaluates whether a cover item is reachable under the current formal environment. It identifies:
     Covered: The item was exercised.

     Uncovered: The item was not exercised within the analysis effort bound.
     Unreachable: The item cannot be exercised due to constraints.
     Deadcode: The item is inherently unreachable, even without constraints.
This analysis helps detect overly constrained environments and unreachable logic.
Checker Coverage
Checker coverage assesses how well the assertions (checkers) verify the design. It determines whether each cover item is within the influence
of any assertion and how effectively it is being checked. Checker coverage is further divided into:
     Cone of Influence (COI)
     Proof Core
     Mutation Coverage
These types vary in precision and computational effort, offering a layered approach to assertion completeness analysis.
Formal Coverage
Formal coverage is the overarching metric that combines both reachability and assertion completeness. It answers the question: "Have I verified
everything I intended to?" by integrating the results of stimuli and checker coverage.




     Functional coverage, which is only evaluated through stimuli analysis, does not incorporate checker results. Consequently, the formal
     coverage result for functional cover items remains identical to the stimuli coverage.




Cover Items
Cover items are the fundamental units of measurement in coverage analysis. Each cover item is analyzed individually by the selected
Coverage Type to define its status. The Coverage metric is then defined as a ratio of cover items that reached the upmost status in that analysis
over the total of cover item.
Cover Items are extracted using Coverage Models, which define what aspects of the design should be analyzed.




Representation of Cover Items
In the Jasper Coverage App, each cover item is a uniquely identifiable element stored in the coverage database. It represents a specific
condition or behavior in the RTL that is subject to coverage analysis.

Structure of a Cover Item
Each cover item includes:
     A unique numerical ID
     A descriptive name
     A reachability condition, which is the logical expression that must be satisfied for the item to be exercised.
These attributes are automatically generated by the tool when the coverage model is created.


Naming Convention
The naming convention used for code cover items encodes detailed information about the item's origin and type. A typical name follows this
format:

 automatic_coveritem_<type_1>_condition<subtype><cover_item_index>_<type_2>_<line>_<subtype_num>_<type_index>

The specifics of the naming convention follow:
     type_1   – branch, stmt, toggle, expression, or fsm.
     subtype   – Type of branch, statement, expression, toggle, or fsm cover item.

     cover_item_index     – Index of all cover items generated.
     type_2   – S for statement, B for branch, E for expression, and T for toggle.

     line   – The location of the cover item.

     subtype_num – For conditions, 0 for true path and 1 for corresponding false path.
     Example: if_expr_then is 0 while if_expr_else is 1

            This information is irrelevant in the case of statements.


     type_index – The index of cover items with the same subtypes, line numbers, and subtype number.
     Example: mux_out = enable ? enable2 ? din_1: din2: din_0; has two if_expr_then on the same line; therefore, their type indexes are
     0 and 1.


     Functional cover items do not follow the above rule. Property-based cover items will inherit the name from the related cover they
     originated from, and the covergroup-based cover items carry the bins names.




Coverage Models
Coverage models are in the center of coverage flows. They define what will be measured during coverage analysis and generates the specific
cover items for those — the elements of the design that will be evaluated for reachability and verification completeness.
Coverage models are categorized into two main types: Code Coverage Models and Functional Coverage Models.
Code Coverage Models
Create cover items based on the RTL structure. It includes:
     Branch Coverage: Tracks conditional branches (if, case, ternary).
     Statement Coverage: Tracks individual executable statements.
     Expression Coverage: Tracks logical expressions and sub-expressions.
     Toggle Coverage: Tracks signal transitions (rise/fall).
     FSM Coverage: Tracks states and transitions in finite state machines.
It is totally based on the code, so it might not capture meaningful functional behavior and might be noisy, generating a significant number of

Functional Coverage Models
Create cover items based on user-defined descriptions of expected design behavior through:
     Properties: Formal specifications of temporal behavior.
     Covergroups: Structured constructs with coverpoints and bins.
Functional models are scenario-driven and noise-free, but might be incomplete due to human error.
Choosing and Combining Models
In practice, both code and functional coverage models are used together:
     Code coverage ensures structural completeness.
     Functional coverage ensures behavioral completeness.
By combining both, you can achieve a comprehensive and balanced verification strategy that covers both the how and the what of the
design.


Code Coverage Models
Code coverage models are automatically generated based on the RTL code. They provide a structural view of the design and are essential for
ensuring that all parts of the code are exercised and verified.
Benefits of Code Coverage Models
     Automatically generated – reduces manual effort.
     Structural completeness – ensures all RTL constructs are considered.
     Supports checker analysis – used in stimuli and checker coverage types.


Branch
The Branch Coverage Model evaluates the execution of decision blocks in the RTL code. It ensures that all possible branches in conditional
constructs are exercised during formal analysis. Each branch condition is treated as a distinct cover item, letting you verify that all logical paths
through the design have been explored.
Branch coverage applies to the following RTL constructs:
     if, else if, and else   statements (even implicit elses)
     case   and casez statements
     Ternary (? :) expressions

     Continuous assignments (when enabled)
Each logical path through these constructs is scored as a separate branch cover item.


How It Works in Jasper Coverage App
For each conditional construct:
     Each branch (true/false or case option) becomes a cover item.
     Implicit branches in IF constructs are also scored.

     The tool can optionally include continuous assignments using:
                 Command line options: jg -cov_init -include_assign_scoring
                 Tcl: check_cov -init -include_assign_scoring

                 CCF: set_assign_scoring

Statement
The Statement Coverage Model evaluates whether each executable statement in the RTL has been exercised during formal analysis. It
ensures that every line of code is triggered at least once, providing a foundational level of structural coverage.
Each statement is treated as a distinct cover item, letting you verify that all parts of the design logic are active and observable under the current
verification environment.
Statement coverage applies to a subset of RTL constructs, including:
     if, else if, and else   blocks

     case   statements
     Blocking and non-blocking assignments
     Module instances
     Continuous assignments (when enabled)
Each individual statement within these constructs is scored as a separate cover item.


How It Works in Jasper Coverage App
For each supported statement:
     A cover item is created for the statement itself.
     The reachability condition is based on the logical context, not the sensitivity list (as in simulation).
     Empty branches (for example, empty else) do not carry a statement cover item.

     In formal mode, many statements have a reachability condition of true, since they are evaluated in all reachable contexts.

Expression
The Expression Coverage Model evaluates whether logical expressions in the RTL can independently evaluate to both true and false. It
provides a fine-grained view of how conditions and sub-conditions behave during formal analysis, going beyond simple control flow to assess
the logical correctness of expressions.
Each expression and its sub-expressions are treated as distinct cover item, letting you verify that all logical paths and combinations are
exercised.
Expression coverage applies to:
     Conditional expressions in if, case, and ternary (? :) constructs
     Boolean and bitwise operations
     Relational and equality comparisons
     Nested and compound expressions
Supported operators include:
     Relational: >, >=, <, <=, ==, !=

     Logical: !, &&, ||

     Bitwise: &, |, ^, ~
     Reduction: &, |, ^, ~&, ~|, ~^

     Conditional: ?:


How It Works in Jasper Coverage App
     Each expression is decomposed into levels of sub-expressions.
     Each level is scored using control scoring, which checks whether changes in inputs affect the output.
     The tool evaluates all combinations of operand values to determine if the expression can evaluate to both true and false.

     Expression coverage can be enabled for continuous assignments using:
           Tcl: check_cov -init -model expression -expr_coverable_statements contassign

           CCF: set_expr_scoring -control and set_expr_statements -contassign

Short-Circuit Mode
Short-circuit mode optimizes expression evaluation by skipping operands that do not affect the result. This is particularly useful for logical
operators like && and ||.


How It Works
     In A && B, if A is 0, B is not evaluated.

     In A || B, if A is 1, B is not evaluated.

This behavior is reflected in the coverage model by excluding unnecessary operand evaluations, reducing noise and improving
performance.
Enabling Short-Circuit Mode
     Tcl: check_cov -init -vlog_short_circuit
     CCF: set_expr_scoring -short_circuit

VHDL logical operators (and, or, nand, nor) are short-circuited by default for BIT and BOOLEAN types.

Toggle

The Toggle Coverage Model measures the activity of signals in the design by tracking their transitions – specifically, rising (0 → 1) and
falling (1 → 0) edges. It ensures that all relevant signals are actively switching, which is critical for identifying unused or static logic.
Each toggle event (rise or fall) is treated as a distinct cover item, letting you verify that signals are not stuck or under-constrained.
Toggle coverage applies to:
      Single-bit signals (for example, reg, wire, logic)

      Vector signals (for example, reg [3:0])
      Multidimensional arrays (for example, reg [2:0] addr[0:1])

      Interface ports and modport signals (when enabled)
Each bit of a signal is scored independently for both rising and falling transitions.


How It Works in Jasper Coverage App
For each signal bit:
      Two cover items are created:
            Rise: !signal ##1 signal

            Fall: signal ##1 !signal
     A toggle item is considered covered only if both transitions are observed.



 Best Practices
    Control scope and granularity: Use configuration options to limit toggle scoring to relevant modules, ports, or signal types. This helps
    reduce noise and improves analysis focus.
    Example: check_cov -init -model toggle -toggle_ports_only

    Use toggle coverage to detect under-constrained environments: If a signal never toggles, it may indicate missing stimuli, overly
    restrictive assumptions, or dead logic.
    Combine with stimuli coverage: Use reachability analysis to determine whether untoggled signals are truly unreachable or simply
    unexercised.
    Use mutation-based toggle analysis for precision: When available, enable stopat or stuckat mutation modes to assess whether
    toggling affects assertion outcomes.
    Review multidimensional and vector signals carefully: Ensure that all bits of wide buses or arrays are toggling as expected.
    Correlate with checker coverage: A signal that toggles but is not covered by any assertion may indicate a verification gap.


     Toggle coverage can be configured using various switches in check_cov -init or CCF files to control scope, granularity, and signal
     types. Check the Tcl Help and the Jasper Verisium Manager Integration User Guide to see all of them.

FSM
The FSM (Finite State Machine) Coverage Model evaluates the control logic of a design by tracking:
     All states defined in an FSM
     All transitions between those states
This model ensures that the FSM behaves as expected under all conditions and that no state or transition is left untested. It is particularly
important for verifying protocols, sequencers, and control-intensive logic.
Where FSM Coverage Applies
FSM coverage applies to:
     Synchronous state machines implemented using always blocks.

     FSMs with clearly defined state registers and next-state logic
     Designs where state transitions are driven by a clock and reset.
Each state and transition are scored as a separate cover item.


How It Works in Jasper Coverage App
The tool identifies FSMs by analyzing:
     A state vector (typically a reg or logic signal)

     A combinational block that computes the next state
     A sequential block that updates the current state on a clock edge
For each FSM:
     A state cover item is created for every unique state.
     A transition cover item is created for every valid state-to-state transition.

     Jasper Coverage App does not support arc coverage, reset states, or hold transitions.

Coverage Types
Coverage types define how the cover items are analyzed. In Jasper Coverage App, two primary types of analysis are performed: Stimuli
Coverage and Checker Coverage, the combination of their results is the Formal Coverage Metric. An additional Coverage Type is the
Coverage Bound Analysis, performed over the undetermined assertions.




Stimuli Coverage
Stimuli Coverage evaluates the reachability of cover items. It determines whether the design is fully exercised by the environment setup,
identifying any deadcode or overly constrained portions of the design. This analysis ensures that all parts of the design are reachable and can
be activated during verification, helping to uncover issues in the testbench or design constraints.
Checker Coverage
Checker Coverage analyzes the completeness of the formal verification testbench, which consists of the assertions written by you. It assesses
how effectively each assertion describes the design by evaluating the impact of cover items on the assertion proof. Note that checker coverage
is only measured for code cover items.
Checker Coverage includes the following modes:
     Cone of Influence (COI): Identifies the portion of the design logic that can affect a given assertion. This helps determine the scope and
     relevance of each checker.
     Proof Core: Evaluates the minimal set of logic required to prove a property.
           Normal Precision: Balances accuracy and performance.
           High Precision: Offers a more detailed analysis, useful for critical properties.
     Mutation Analysis: Tests the robustness of assertions by introducing small changes (mutations) in the design and checking whether the
     assertions detect them. This mode helps assess the sensitivity and effectiveness of the checkers.

     Coverage offer an additional type called per-property checker that runs mutation and return results aggregated per-property.

Formal Coverage Metrics
The combined results of Stimuli and Checker Coverage form the final formal coverage metrics. This aggregated view provides a
comprehensive understanding of both the design's reachability and the quality of the verification intent.
Bound Analysis
In addition to the above, Jasper Coverage App performs Bound Analysis, which evaluates whether assertions have been sufficiently explored
within the design. It indicates the depth and extent of the verification, helping you understand how far the formal engine has progressed in
proving each property.

Interpreting Unreachable vs Dead Code
     Unreachable: The item is blocked by the formal environment or constraints (for example, assumptions, resets, bindings). It might be
     reachable if constraints are relaxed, or the environment is adjusted. Unreachable items can hide bugs if the environment is overly
     restrictive. Design constant propagation occurs because of current design configuration (for example, hardwired signals), but if the
     design were modified (for example, parameterized), the item could become reachable.
     Dead Code: The item is structurally impossible to exercise, even in a fully unconstrained environment. This usually indicates redundant
     logic, impossible encodings, or design invariants that exclude certain behaviors.

Checker Coverage – The Completeness Analysis
Checker Coverage evaluates the effectiveness and completeness of the assertion set in monitoring and verifying the design. While Stimuli
Coverage focuses on reachability, Checker Coverage answers a different question:
"Is the design logic that can be exercised actually being checked by assertions?"
This analysis helps identify verification gaps where portions of the design are reachable/exercisable/coverable but not checked by any
assertion, potentially allowing bugs to hide from the verification.
The goal of Checker Coverage is to:
     Assess how much of the design is checked by assertions.
           Qualify code cover items by determining whether they influence any assertion.
     Highlight undetectable regions that may require additional properties.


Checker Coverage Modes
The Jasper Coverage App provides multiple modes for assertion completeness analysis, each with different precision and effort levels:
     Cone of Influence (COI): A structural fan-in analysis that traces backward from each assertion to its influencing inputs.
           Characteristics: Fast, engine-free, low effort.
           Use case: Initial check for assertion coverage.
     Proof Core: Identifies the portion of the design actively used by formal engines during proof.
           Precision levels:
                 Normal Precision: Balanced performance and detail.
                 High Precision: More granularity, deeper insight for critical assertions.
           Use case: Detailed analysis after COI to assess actual impact on assertion.
     Mutation Coverage: Measures assertion effectiveness by mutating the design and observing whether assertions detect the changes.
           Characteristics: Highest precision, highest effort.
           Use case: Critical/high-risk areas where maximum confidence is required.

How COI works
1. Start from an assertion and trace backward to its influencing inputs.

Proof Core
Proof Core provides a precise view of assertion coverage by identifying the portion of the design actively used by formal engines during
proof. Proof Core reflects actual proof behavior, it refines COI, which is purely structural, isolating the logic essential to prove assertion.


How Proof Core Works
Proof Core applies isolation techniques to different regions (a region is a subset of the design defined by a signal boundary and its driving
logic). Proof Core evaluates which regions are truly necessary for assertions to achieve a proved result:
     If an assertion still proves after disconnecting a region, that region is not essential for the proof.
     If an assertion fails when a region is disconnected, that region is required for the assertion to hold.

Proof Core Precision Modes
The Jasper Coverage App offers two precision modes for Proof Core analysis. The main difference between each mode is the technique used
to define the observation points that bound the design region for the analysis, letting you balance between accuracy and performance
depending on their verification goals.
     Normal Precision (Default Mode):
          Uses flip-flops (flops) as the boundary points for Proof Core extraction.
          All logic driving a checked flop is considered checked, even if only part of it contributes to the proof.

             Offers coarse granularity, which may overestimate coverage in some cases.
             Highly efficient, with minimal overhead – ideal for large designs or early-stage analysis.
       High Precision:
             Includes combinational logic in addition to flops when forming the proof boundary.
             Provides finer granularity, enabling the tool to distinguish between logic that is truly essential and logic that is structurally nearby
             but unused.
             Helps identify additional uncovered code that may be missed in normal mode.
             Requires more computational effort, as it introduces additional engine iterations and deeper analysis.
When to Use Each Mode
       Use Normal Precision for fast, broad coverage assessments or when performance is a concern.
       Use High Precision when preparing for signoff, after running normal precision, for debugging coverage gaps, or analyzing critical
       properties that require detailed proof traceability.

Best Practices – Proof Core

    Use Proof Core for Precision:
    Proof Core exposes situations where assertions appear successful but do not truly verify meaningful portions of the design. Because it is
    proofbased rather than structural, Proof Core provides a more accurate representation of what is actually verified than COI.
    Start with Normal Precision:

    earlystage analysis, where performance is a priority.
    Switch to High Precision for Critical Areas:
    Use High Precision when analyzing safety-critical logic, debugging suspected coverage gaps, or validating signoff completeness.
    High Precision uncovers logic and behaviors that may be over-approximated as covered in Normal Precision by increasing granularity
    inside combinational logic.
    Investigate Unchecked Items:

    Correlate with Stimuli Coverage:
    If a region is reachable by Stimuli Coverage but absent from the Proof Core, it indicates insufficient assertion coverage. This
    correlation is a strong signal of verification intent gaps and often points to missing or incomplete properties.
    Combine with Mutation for Maximum Confidence:
    Use Mutation Coverage after Proof Core to validate that the logic marked as covered is not only used in proofs but also sensitive to
    changes.


Mutation
Mutation Coverage is the most precise checker coverage mode available in the Jasper Coverage App. It evaluates how sensitive assertions
are to changes in the design by introducing controlled modifications (mutations) and observing whether these changes are detected by the
assertion typoset.

                                                     Jasper Coverage App User Guide
                                              Jasper Coverage App Overview--Coverage Types



While COI and Proof Core determine whether logic is structurally connected to assertions or required for proof, Mutation Coverage actively
tests whether assertions can detect incorrect behavior. In other words, it verifies not only that logic is used in proofs, but that it is functionally
protected.

How Mutation works
     The tool automatically introduces mutations (small changes) accordingly to the mutation mode selected at specific points in the design.
     Each cover item is a mutated point. Mutation checks each mutated point individually.
     Mutation engines try to prove the existing assertions to determine whether they can detect the mutation.
           If any assertion fails, the mutated cover item is checked.
           If all assertions pass, the mutated cover item is undetectable.




     If a mutation can be introduced at a given point without triggering an assertion failure, that logic is not effectively verified.


Mutation Modes
Mutation Coverage supports two distinct modes of logic change, each designed to test different aspects of assertion sensitivity. These modes
define how the cover item is altered during analysis and how they are analyzed based on the coverage model support.
     Stopat Mode:
           In this mode, the driver of the signal associated with the cover item is replaced by a free driver.
           This allows the signal to take on any value, independent of its original logic, simulating a scenario where the signal behaves
           unexpectedly.
           If the mutation causes an assertion to fail, it confirms that the assertion is sensitive to changes in that signal.
           Applicable to: All code coverage models – branch, statement, expression, and toggle.
     Stuckat Mode:
           This mode performs two separate mutations:
                 One forces the signal to a constant value of 0.
                 The other forces it to a constant value of 1.
           These mutations simulate scenarios where the signal is stuck at a fixed value, helping detect whether assertions can catch such
           faults.
           Applicable to: Only toggle cover items, as it specifically targets signal transitions.


StopAt Mutation Coverage at Statement Cover Items

For Statement cover items, Mutation Coverage applies the StopAt mode.
In this mode, the righthand side (RHS) of each statement associated with a cover item is replaced by a free driver. This means that the value
assigned by that statement becomes unconstrained and can take any value, independent of the original logic.
The tool then reruns formal analysis to determine whether this change causes any assertion to fail.
     If at least one assertion fails, the statement is Checked.
     If no assertion fails, the statement is Undetectable.
Interpretation:
StopAt mutation at the statement level answers the question: "If this assignment produced an arbitrary value, would any assertion notice?"
If the answer is no, then bugs in that statement could escape detection.

StopAt Mutation Coverage at Branch Cover Items
For Branch cover items, Mutation Coverage also applies the StopAt mode.
In this context, StopAt is equivalent to replacing the entire body of the branch with free drivers. The condition controlling the branch remains
intact, but the effect of executing that branch is no longer defined by the original RTL.
The assertions are then evaluated against this mutated design.
     If any anyassertion fails when the branch body is replaced, the branch is Checked.
     If the assertion still proves, the branch is Undetectable.
Interpretation:
Branch-level StopAt mutation answers: "Does the functional behavior executed under this branch matter to any assertion?"
A branch can be structurally relevant (COI) and even used in proof yet still be undetectable under mutation – indicating incomplete verification
intent.

StopAt Mutation Coverage at Expression Cover Items

Per-Property Checker
Per-Property Checker Coverage is an assertion-centric checker coverage type that provides coverage visibility on a per-assertion basis,
rather than aggregating results across the entire formal environment.
Traditional Checker Coverage (COI, Proof Core, Mutation) evaluates coverage with respect to all assertions together. While this is effective
for measuring global completeness, it makes it difficult to answer questions such as:
     Which assertion provides better coverage?
     Which assertions are most useful for bug hunting?
     Which assertions are overly complex and could benefit from simplification or stopats?
PerProperty Checker Coverage addresses these limitations by isolating and analyzing each assertion independently.
Key Idea
PerProperty Checker Coverage runs proof-based mutation analysis for each target assertion, restricted to the cover items within that
assertion's Cone of Influence (COI).
Each assertion is analyzed in isolation, producing dedicated coverage metrics that reflect how effectively that single assertion checks the
design, independent of any other properties in the environment.
Key Distinction
     Traditional Checker Coverage: "Is this logic checked by any assertion?"
     Per-Property Checker: "How much of the design logic does this specific assertion check?"


How Per-Property Checker Coverage Works
Per-Property Checker Coverage focus all its resources in finding checked items. At a high level, the flow is as follows:
  1. Select target assertion(s)
     One or more assertions are specified as the analysis targets.
     check_cov -measure -type per_property_checker -property <property_list>

  2. Compute COI per assertion
     For each assertion, the Coverage App identifies the set of cover items (currently toggle-based) within its COI.
  3. Apply Mutation Coverage per assertion
     Mutation analysis is performed independently for each assertion, using proof-based techniques to determine which cover items are
     detected by that assertion.
  4. Generate perassertion reports
     Results are reported per property, rather than merged across all assertions.
Each assertion runs in its own dedicated partition, using custom engines to:
     Minimize proof setup overhead
     Ensure fair resource allocation
     Scale efficiently across many assertions

Coverage Bound Analysis
Coverage Bound Analysis evaluates the quality and depth of an undetermined assertion by examining how thoroughly the design has been
explored relative to the assertion's intended behavior.
An assertion is considered undetermined by Formal Property Verification (FPV) when it does not converge to either:




March 2026                                                              74                                            Product Version 2026.03
                                                   Jasper Coverage App User Guide
                                        Jasper Coverage App Overview--Coverage Bound Analysis



     a proof, or
     a counterexample (CEX)
In this situation, the formal engines explored the design up to a certain depth (number of cycles), found no violation, but did not exhaustively
prove correctness.
Coverage Bound Analysis exists to answer one very specific question:
"Is the explored depth deep enough to cover the meaningful behavior related to this assertion?"
It does not attempt to prove correctness. Instead, it assesses whether the bounded result is credible given what is known about the design
behavior.
What Bound Analysis Is NOT
Before going further, it is critical to eliminate common misconceptions:
     Bound Analysis does not prove assertions.
     Bound Analysis does not increase the bound.
     Bound Analysis does not evaluate assertion correctness.
     Bound Analysis does not replace Proof Core or Mutation.
Bound Analysis evaluates the quality of a bounded result by comparing how deeply the design was explored relative to the behavior the
assertion is meant to check.



Key Concepts for Bound Analysis
1. Assertion Bound (FPV Bound)
The assertion bound (also referred to as the FPV bound) is the maximum trace length explored by the formal engines when the assertion
remained undetermined.
Example
     FPV bound = 5→ All reachable behavior up to 5 cycles from reset was explored.




This bound indicates how far the formal engines searched, not that the assertion was proven correct beyond this depth.
Important:
The assertion bound reflects exploration depth, not correctness. An undetermined assertion with a large bound may still miss relevant behavior
that occurs later.
2. Cover Item Bound
Each covered cover item (from Stimuli Coverage) has a minimum trace length at which it becomes reachable.

                                                   Jasper Coverage App User Guide
                                        Jasper Coverage App Overview--Coverage Bound Analysis



Example
     A FIFO full condition might require 18 cycles.
     A state transition might require 7 cycles.
This value is the Cover Item Bound.




     Unreachable or Deadcode Items
Cover items classified as Unreachable or Deadcode by Stimuli Coverage are reported with a bound value of "Infinite."
     These items cannot be exercised under any circumstance.
     They are treated as out of COI, since no assertion can verify logic that cannot be exercised.
     They are automatically excluded from Coverage Bound Analysis.


     Cover Item Bounds Reported as a Range (min–max)
Some cover items are reported with a bound range, shown as:
<min_bound> - <max_bound>
This range indicates:
     Minimum bound: the biggest trace length where the cover item was not covered.
     Maximum bound: the shortest trace where the cover item was covered.


This typically occurs when the cover item can be exercised at multiple depths.




Imagine that for a given cover Item, three engines found different traces:
     Engine 1 found a trace where the CI is unreachable up to cycle 3, and it is covered only from cycle 16, so, from cycle 3 up to 16, this
     engine could not determine conclusive results, therefore, the CI could be covered or unreachable within.

     Engine 2 found a trace where the CI is unreachable up to cycle 8, a conclusive convered result was only found on cycle 14. The results
     between cycle 8 to 14 are inconclusive.
     Engine 3 found a trace where the CI is unreachable up to bound 5, and it was covered from bound 12; results between bounds 5 to 12 are
     inconclusive
The CI bound result will take in consideration all conclusive results found by the engines for the unreachable and the covered cycles:
     Minimum bound = 8
           From engine 2, it is guaranteed that the CI will be unreachable up to cycle 8. Other engines found a small cycle; however, they could
           not determine the result on cycle 8.
     Maximum bound = 12
           From engine 3, it is guaranteed that the CI will be covered from the cycle 12. Other engines were only able to determine covered
           results in deepest cycles.
The CI final bound result is (8 – 12). This means that up to cycle 8, the CI is guaranteed unreachable, and from cycle 12, the CI is guaranteed
covered. The results are undetermined from 8 to 12, meaning that it can be unreachable or covered in this range.

     CI's that have min_bound = max_bound are called minimum CIs. The reported bound is a unique value. CIs with a ranged bound result are
     called non-minimum CIs.



3. Meaningful covers (In COI)
Coverage Bound Analysis evaluates only meaningful covers for a given assertion.
Meaningful cover items consist of:
     Code coverage items that are:
           reachable by stimuli, and
           within the COI of the assertion
     User-defined functional covers that are relevant to the assertion.
Because user-defined functional covers do not participate in checker modes computation, they are not collected through the assertion COI
directly. Instead, a user cover is considered meaningful for an assertion when:
     its fan-in shares at least one signal with the assertion's fan-in,
     excluding declared clocks and resets.
The total number of meaningful cover items for an assertion is reported as "In COI" in the Assert Analysis Summary View.
All meaningful coverage items – together with:
     stimuli status,
     cover item bound, and
     bound analysis classification
are listed in the Assert Analysis Detailed View.

How Bound Analysis Works
The main idea behind Coverage Bound Analysis is to compare the bound reached by an undetermined assertion with the bounds
required to exercise the assertion's meaningful cover items.
Because Stimuli Coverage is independent of assertion status, it reports the minimum trace bound necessary to exercise each cover item.




March 2026                                                               79                                    Product Version 2026.03
                                                    Jasper Coverage App User Guide
                                         Jasper Coverage App Overview--Coverage Bound Analysis



If a cover item:
      is reachable by stimuli, and
      lies within the COI of the assertion,
then it represents behavior that is at least minimally related to that assertion.
Therefore, it is reasonable to expect that an assertion should explore at least as deep as the deepest meaningful cover item in its COI.
For each undetermined assertion, Coverage Bound Analysis performs the following steps:
      Identify meaningful cover items (code and functional).
      Determine their stimuli status of those cover items (covered or uncovered)
            Covered items → Covered CIs
            Uncovered items → Undetermined CIs
            Unreachable items are excluded from analysis
      Retrieves each cover item bound.
      Compares the cover item bound against the assertion FPV bound.
      Assigns a Bound Analysis Status to each cover item.



Bound Analysis Status
Coverage Bound Analysis classifies cover items into three categories:
InBound Covers
      Stimuli status: Covered
      Cover item bound ≤ assertion bound
Interpretation:
      The assertion explored deeply enough to exercise this logic.
      Coverage is considered adequate.


Covers Beyond Bound
      Stimuli status: Covered
      Cover item bound > assertion bound
Interpretation:
      The assertion did not explore deeply enough to reach this logic.
      Indicates a potential coverage gap.
These items represent meaningful behavior that was not exercised during bounded exploration.
Undetermined Covers
      No meaningful bound available
      Stimuli status: Uncovered
Typically caused by:
      insufficient stimuli convergence
      incomplete exploration
These require investigation but do not automatically invalidate the assertion bound.

Bounded Coverage Metric
Bounded Coverage is the primary quantitative result of Coverage Bound Analysis.
It is defined as:
InBound Covers / Total Meaningful Covers (In COI)
This metric provides insight into:
     how much relevant logic was exercised within the bounded proof, and
     how much potentially related behavior remains unexplored.


Covered CIs Bound
Two metrics report coverage items within the assertion COI that were covered by stimuli, but require a deeper trace length than the
assertion FPV bound:
     Covered CIs Beyond Bound
     Number of meaningful cover items whose minimum cover item bound exceeds the assertion FPV bound.
     Covered CIs Max Bound
     The highest minimum bound among all meaningful cover items classified as Beyond Bound.
These metrics represent a real and concrete gap between:
     the depth explored by the assertion, and
     the minimum depth required to exercise meaningful, related design behavior.
Items in this category indicate that the assertion did not explore deeply enough to exercise all relevant logic within its COI.


Undetermined CIs Bound
Two metrics report meaningful cover items within the assertion COI that are uncovered by stimuli and therefore have no valid cover item
bound:
     Undetermined CIs
     Number of meaningful cover items for which no minimal bound could be determined due to lack of stimuli coverage.
     Undetermined CIs Max Bound
     The maximum depth explored by the formal engines while attempting (but failing) to exercise these undetermined cover items.
Undetermined cover items may represent a coverage gap, especially when the Undetermined CIs Max Bound is greater than or close to the
assertion FPV bound.This situation suggests that:
     the assertion explored to a certain depth, but
     meaningful logic in its COI remains unexercised due to insufficient stimuli or incomplete convergence.
Unlike Beyond Bound items, undetermined items do not automatically indicate insufficient assertion depth, but rather highlight potential
stimuli or environmental modeling limitations that warrant further investigation.

Best Practices - Coverage Bound Analysis

 Best Practices
    Use Bound Analysis for Undetermined Assertions:
    Apply bound analysis when an assertion does not converge to a proof or counterexample. It helps assess whether the bounded result is
    meaningful or requires further exploration.
    Use Bound Analysis Correctly:
    Bound Analysis does not tell you "the assertion is correct." It tells you whether the bounded result explored enough of the design to make
    that claim plausible.
    Used correctly, it becomes:
       A risk assessment tool
       A signoff justification aid
       A bridge between formal depth and design behavior
    Compare Assertion and Cover Item Bounds:
    Focus on cover items within the assertion's COI. If they are beyond the assertion's bound, the assertion may not have explored all relevant
    logic.
    Extend Proof Effort Strategically:
    If many items are beyond the assertion's bound, consider increasing the bound depth to allow deeper exploration.
    Refine Constraints to Improve Convergence:
    Undetermined CIs may be an indicative of overly complex or loose environments which can hinder convergence. Tighten or simplify
    constraints to reduce the state space and help the engine reach deeper states more efficiently.
    Use in Bound Signoff Methodology:
    Sometimes, invest in full proof may require a lot of time and effort, consider apply a methodology based on Bound Analysis to signoff with
    confidence.
    Document Bound Analysis Outcomes:
    Record which assertions were bounded, their depth, and the cover item distribution. This supports traceability and helps justify signoff
    decisions.
    Combine with Checker and Stimuli Coverage:
    Use bound analysis alongside checker and stimuli results to build a complete picture of verification completeness and identify areas
    needing refinement.

The Coverage Process
Coverage in the Jasper Coverage App is not a single operation, but a repeatable, iterative
process in the lifecycle of the design. Each phase produces information that feeds the next, and
most phases are revisited multiple times as the verification environment evolves.




Phase summary:
  1. Initialize Coverage
     Activate Coverage and define what will be measured. Select coverage models, change
     defaults and determine analysis scope
  2. Measure Coverage
     Run measurements to gather metrics for Stimuli Coverage, Checker Coverage and Bound
     Analysis
  3. Analyze Results
     Review summaries and details to identify reachability issues, unchecked regions, insufficient
     assert bound items, and undetermined covers.
  4. Apply Waivers (optional – highly recommended)
     Exclude items intentionally (with justification) when they are irrelevant, structurally dead, or
     out of scope. Waivers do not "fix" coverage; they document intent.

  5. Export/Import Session Data (optional)
     Aggregate coverage results from multiple runs, configurations, or engineers to form a
     comprehensive view.
  6. Reports
     Generate summary and detailed artifacts for reviews and archival. Reports should carry
     context (waivers, bounds) in addition to metrics.


Iteration is Expected

assumption of the coverage methodology.

Bounds: Respecting FPV Depth During Checker Analysis
Each property evaluated by FPV has an FPV bound that indicates how deep engines explored for

      FPV bound to flag "Covered CIs Beyond Bound" and "Undetermined CIs" cases that
      require deeper exploration or environment refinements.
Do I need to run prove before Coverage?
Yes. You should run prove before Coverage to ensure alignment between FPV and Coverage

and to establish consistent proof data for all analyses.

      enabled and some properties are UNPROCESSED, Proof Core will:
        1. schedule those properties for proof,
        2. attempt to bring them to PROVEN, and
        3. compute the Proof Core use information from those newly proven properties.

      because:
             property statuses may shift across runs,
             Proof Core may need to complete expensive proofs for the first time inside Coverage,
             FPV bounds may differ across merged sessions,
             Coverage results become sensitive to license, engine, and job availability,
             overall result consistency becomes harder to guarantee.
      Running prove first stabilizes all of this. Coverage will still function without a prior prove, but
      the results will not be fully aligned with FPV and may lack the determinism expected in
      verification signoff environments.

Checker Mode Progression and Result Propagation
As explored in Chapter 2, all checker coverage modes (COI, Proof Core NP, Proof Core HP,
Mutation) share a unified propagation mechanism:
Forward Propagation
      Undetectable items from less precise modes (for example, COI) are forwarded into more
      precise modes.
      This ensures high-effort engines focus only on items needing deeper analysis.
Backward Propagation
      Checked items obtained from more precise modes (for example, Mutation) propagate
      backward to less precise modes.
      This avoids redundant re-analysis.

      Run prove Before Coverage

      avoids unstable or inconsistent coverage behavior.
      Choose Coverage Types Deliberately

      NP, Proof Core HP, and Mutation in separate commands.
      Monitor and Respect FPV Bounds
      FPV bounds constrain how checker modes interpret detectability; shallow bounds or "Beyond
      Bound" results indicate the need for deeper proof or environment adjustments.
      Allocate Resources Appropriately
      Understand how licenses, jobs, engines, and time limits impact performance; size resources
      intentionally for Stimuli, Checker, or Mutation runs.
      Measure Coverage in a Logical Progression
      Use the recommended order – COI → Proof Core NP → Proof Core HP → Mutation – to

Waivers
During coverage analysis, you may identify cover items that are not relevant to the current
verification scope – for example, items that are intentionally unreachable due to configuration. In
such cases, you can waive those items so they are excluded from coverage metric calculations
and removed from the analysis panes, while remaining traceable in the Waiver Table.
Typical reasons to waive
      The item was already verified in another formal session or in simulation and does not need to
      be re analyzed in this session.
      You want to avoid spending resources on items that are out of scope or not meaningful
      for the current project.

      Waivers are not a substitute for fixing constraints, adding assertions, or increasing effort.
      Investigate first; waive only when the exclusion is intentional and justified.

Exporting and Importing a Waiver File
A waiver file is a Tcl script that reproduces previously created waivers. You can export waivers
from one session and import them into another (for example, a new configuration or an updated
RTL drop).


Export

 check_cov -waiver -export -file <file_name>

The tool writes waivers in Tcl and appends a -persistency checksum to each waiver line to help
reidentify items across sessions and minor RTL edits.


Import

 check_cov -waiver -import -file <file_name>

During import, the tool matches waivers using the persistency checksum plus additional
attributes (file path, hierarchy, source location, expression, and item type), which provides
robustness against small RTL changes (comments/whitespace/line adjustments). Then it returns
a dictionary of successful, updated, repeated, and failures waivers imported.
      Successful – Successfully imported
      Updated waivers – item found, but attributes changed (for example, new RTL path or moved
      instance). These are flagged for review in the Waiver Table.
      Repeated waivers – waivers already created or imported from previous waiver files.
      Failed waivers – no matching item (for example, hierarchy or expression changed
      semantically). A fully successful import reports INFO (ICOV053); imports with failures are
      reported as WARNING (WCOV115).
For the failed waivers, the tool tries to find options that could match them and suggest it to you,
letting you inspect possible cover item for waiving.

      To import a waiver file, although it is in a Tcl format, use the check_cov -waiver -import
      command, and not the include our source.

Recommended Coverage Flow - Putting It All
Together
This section provides a prescriptive methodology for running Jasper Coverage to achieve high
confidence verification closure. It outlines what to run, in what order, why each step matters, and
what evidence should be produced to support signoff.
The flow is intentionally iterative. Coverage is not a one-shot process: it evolves as constraints,
properties, convergence strategies, and the design itself mature.


Step-by-step Coverage Signoff Flow
0) Preconditions
Before running coverage:
      RTL and constraints are elaborated
      Assertions are available and structured
      Coverage initialization is completed (Section 3.2)
      covdb output location is chosen


1) Initialize Coverage Models
Ensure the correct coverage models and scope are configured:
      Code models: Branch, Statement, Expression, Toggle, FSM
      Functional models: cover properties and covergroups
      Scope filters (instances, modules, DUT) are applied
      Model options are set (for example, short-circuiting, FSM options)
This defines what will be measured across all subsequent steps.

2) Measure Stimuli Coverage (Reachability First)
Run stimuli analysis to determine whether relevant logic can be reached.
Investigate:
      Unreachable / Deadcode items
             Fix constraints

                                           Jasper Coverage App User Guide
                  Getting Started with Coverage--Recommended Coverage Flow - Putting It All Together



             Adjust parameterization
             Remove overconstraints
             Waive only when intent is explicit
      Uncovered items
             Increase exploration depth
             Add cover properties
             Improve environment modeling
Proceed once the design's reachable space is understood and justified, to avoid masking bugs due
to overconstraints.

3) Checker Coverage Pipeline
Checker coverage determines whether the assertion set provides sufficient checking for the
reachable logic.
A recommended progression:
3.1 COI
      Fast structural analysis
      Identifies Out-of-COI / Undetectable regions
      These regions indicate areas unchecked by assertions
Action: Add or refine assertions until major logic cones are connected, or waive logic that is not
meant to be checked.
3.2 Proof Core — Normal Precision
      Uses flop level abstraction to compute which logic contributes to proofs
      Helps identify missing or weak assertions
      Reveals overconstraining environments
Action: Strengthen assertions or refine constraints.
3.3 Proof Core — High Precision (Fine Proof Usage)
      Adds combinational precision refinement
      Identifies subtle coverage gaps
      Increases confidence for signoff areas

Recommended: Apply this level to critical or high complexity logic.
Action: Strengthen assertions or refine constraints.

4) Bound Analysis (For Undetermined Assertions)Bound Analysis correlates assertion FPV
bounds with stimuli bounds:
      Covered items beyond bound → may require deeper search or assumption fixes
      Undetermined items with deep observed depths → stimulus convergence issues
Bounded signoff is acceptable when:
      Bounded coverage is high
      Bounds are explained and documented
      Residual risk is consciously accepted
5) Mutation Coverage (Selective, Highest Confidence)
Mutation analysis verifies whether assertions detect injected bugs.
      Applied selectively to critical logic cones
      Requires strongest engines and highest computational effort
      Undetectable mutations represent true verification holes
Action: Strengthen assertions, expand conditions, or improve environment modeling until no
Undetectable mutations remain in critical areas.


6) Per-Property Checker (Auxiliary, Optional)
Per-Property Checker helps:
      Rank assertions by effectiveness
      Identify redundant or weak assertions
      Prioritize areas for deeper analysis (for example, Mutation)
Not a signoff requirement – used for optimization.
7) Waivers (Governance)
Apply waivers only after investigation.
Each waiver should include:
      Reason / justification

      Similar initialization settings
      Same elaborated design structure

9) Reports (Final Evidence for Review and Signoff)

      Assertion summaries

      Session context (models, scope, bounds)

Automatic Target Bound – Coverage Contribution to
Bound Signoff Methodology
In addition to Stimuli and Checker Coverage metrics, FPV integrates another key output from the
Coverage App: the Automatic Target Bound.


What Is the Automatic Target Bound
A property’s target bound defines how deep the proof engine must search without finding a
counterexample to provide a baseline level of verification confidence – especially
for Undetermined properties that do not converge even with long runtimes.




There are two types of target bounds:
      User Target Bound
      Bound explicitly set by you.
      Automatic Target Bound
      Bound automatically inferred from Coverage bound analysis based on code cover items and
      meaningful functional cover items related to the assertion.
The Automatic Target Bound acts as a reference point to help you choose an appropriate User
Target Bound.

Computing Automatic Target Bound
The Automatic Target Bound is generated using:

 check_cov -measure -type bound

This command performs bound analysis over a selected set of coverage items.


Selecting Items for Bound Analysis

 set_prove_inferred_target_bound (auto | all | off)

      property.
      all

      to the Covered CI Max Bound metric.
      off

Overview of Formal and Simulation Coverage
Simulation and formal coverage rely on fundamentally different strategies to determine whether a
design has been thoroughly exercised and adequately verified. Each provides unique insights, and
combining them enables stronger, more complete verification closure.
Simulation Coverage measures how effectively a testbench exercises the DUT using stimulus-
driven execution. It scales well to large designs and provides quantifiable metrics, such as block
coverage, functional coverage, and toggle coverage, but it is inherently non-exhaustive. Any
behavior not triggered by the testbench remains unexamined.
Formal Coverage uses mathematical reasoning to exhaustively explore all reachable design
states. It determines whether a coverage item is reachable, unreachable, or conclusively proven
dead code. Because it requires no testbench, formal provides deep visibility into design intent and
corner cases. However, exhaustive exploration can become challenging for very large or highly
complex designs.

Benefits of Combining Simulation and Formal Coverage
When simulation and formal coverage results are merged, verification teams gain the strengths of
both methodologies:
      Simulation provides scalable, high-throughput stimulus-based coverage, efficiently
      exercising broad portions of the design.
      Formal contributes exhaustiveness, identifying unreachable code, completeness gaps, and
      corner-case behavior that simulation may miss.
      Both teams work from a unified, consistent coverage model, enabling clearer
      communication, more accurate reporting, and streamlined signoff.
      Formal analysis can focus only on simulation gaps, improving turnaround time by
      avoiding re-analysis of already covered items.
      Items proven unreachable by formal are excluded from simulation targets, preventing
      wasted effort and improving overall verification efficiency.

Refinement Support
Refinement files can be imported into Jasper to apply exclusions generated during simulation
analysis, or exported from Jasper to propagate formal-based waivers into the simulation
environment allowing simulation and formal waivers/exclusions to stay synchronized.
Import Refinement File into Jasper
Use the following command to import waivers/exclusions identified by simulation (vManager/IMC):

 check_cov -waivers -import -vrefine -file_name <file> [-ucdb db_path [-target target
 -source source]]

This marks the corresponding coverage items as waived inside Jasper, ensuring that formal does
not re-analyze items already excluded during simulation.

 check_cov -waivers -export -vrefine -file_name <file> [-ucdb db_path [-target target

The generated refinement file can then be loaded by vManager/IMC to keep simulation and formal
exclusions consistent.

      Exporting or importing waivers in vRefine format may require additional metadata from the
      UNICOV database. For details on the required options and usage, refer to the Tcl Help
      documentation for the check_cov -waivers command.

Integrating Jasper and vManager or IMC
For flows where Jasper data is collected by vManager or IMC, use the command-line invocation
method with a Coverage Configuration File (CCF). This is especially important when merging
formal and simulation data.


             Jasper writes data and vManager reads it using the UNICOV library. To ensure a
             seamless flow, both tools must use the same UNICOV library version.
             The UNICOV library can be set via the environment variable MDV_XLM_HOME.

             In simulation-formal combined flows, the UNICOV library must match the one used by
             Xcelium. A UNICOV library is shipped with Xcelium. Point MDV_XLM_HOME to the Xcelium
             installation folder.
